# Implementation analysis and diagram scope

This is a source-based description of the current integration branch, not a claim that every optional backend service is deployed in a particular hosted project. No database inspection, migration, account operation or application configuration change was performed for this documentation task.

The DFDs now follow the requested two-entity scope: Admin and the combined Engineers/Architects entity. Secretary and Tool Handler are omitted from the DFDs; their permissions are not reassigned to the field entity. The implementation inventory and system flowchart still describe the actual application roles.

The review covered the frontend entry points, permission definitions, route / module loading, classic movement implementation, current integration adapters, new quantity / materials clients, custody / QR / evidence / retirement modules, account service and SQL contracts. `validation/source-inventory.json` records the source files scanned; `validation/role-routes.json` records the effective route matrix evaluated from `js/permissions.js`. Historical documentation was not treated as proof of current functionality.

The role boundary follows the current UI and its authenticated operation checks:

- **Admin:** inventory / projects / account maintenance, request approval and allocation, release, return inspection, repair / missing resolution, retirement, materials, purchases and reports. Retirement decisions require a different active Admin from the proposer.
- **Engineer and Architect:** equivalent operational routes, with assignment / ownership scope; equipment and material requests, physical custody submissions and receipt, return submission, fault / missing reports, participation-scoped retirement history and issue reporting.
- **Secretary:** consumables catalog / procurement / stock operations, purchase ledger and own account preferences. This role does not receive equipment approval, field-issuance approval, account administration or reports routes.
- **Tool Handler:** equipment / project / movement monitoring, the permitted classic transfer action, activity and own account preferences. Current routes do not grant Admin approval, repair resolution, quantity allocation, retirement or new QR-custody submission authority.

Several boundaries prevent misleading thesis claims:

1. Public self-registration, supplier / technician login, GPS tracking, payment processing and repair costing are not shown. Supplier names and purchase prices are recorded ledger data, not supplier-side system activity.
2. The equipment screen reads historical archive / active flags, but its current UI does not implement equipment archive / restore controls. Equipment retirement is modeled separately; project and consumable archive / restore are implemented.
3. Individual spreadsheet quantity expansion registers distinct permanent Asset IDs. Existing Bulk / legacy aggregate inventory is not silently converted and cannot enter the new physical quantity / custody workflows.
4. Approval reserves equipment. Transfer submission retains sender custody. Only named-recipient physical acceptance transfers custody; return submission retains the original custodian until an Admin accepts each physical unit.
5. Good return items become available at Office; damaged items enter repair; pending, missing and disputed items retain custody / locks and can be followed up individually. Completed inspection items are retained as history.
6. Outward request approval does not deduct stock. Actual issuance does. Issuance analytics must not be described as confirmed field consumption: the current UI displays confirmed consumption as not recorded when absent and has no confirmation-entry workflow.
7. Inbound procurement, outward issuance and purchase ledger records are separate. Saving a purchase does not receive inventory; recording an inbound delivery explicitly changes stock.
8. Invitations, development account creation, email delivery and scheduled snapshot capture depend on deployment capabilities. Saved historical inventory is prospective and cannot reconstruct a date for which no snapshot exists.
9. Demo data and appearance preferences stay in browser storage. The live-only integration screens, account management, consumables and purchases are excluded from demo mode.
10. Level 1 uses nine grouped stores to keep a logical DFD readable. It is not a physical ER diagram: operation receipts and related audit / evidence association tables are grouped with their owning function. The Level 0 / Level 1 actor sets and boundary flows are consistent.

The diagrams retain permanent history and show error / retry decisions at the major points without duplicating low-level form events or every RPC on separate pages. The review and exports were performed locally; no application or database calls were used to render the documents.

The revised flowchart uses a landscape long-bond main menu and twelve portrait long-bond workflow pages. A-L identify the module pages; X/Y are the two approved-request release continuations. Same-page numbered connectors carry reverse or cross-lane jumps without drawing upward or leftward arrows. Routine completion descends directly to a terminal. Native-rendered arrow geometry, decision ports, connector pairing and reciprocal page references are checked by `source/audit-professional-flow.cjs`. Page 7 preserves the implemented Tool Handler classic transfer and failed-receipt follow-up; this role is still intentionally absent from the separately scoped two-entity DFDs.
