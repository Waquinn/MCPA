# Workstream A database contract

Migration: `supabase/migrations/202610250001_quantity_material_requests.sql`. This file is a review artifact and has not been applied to Supabase or any existing database. The reserved filename was unused when implementation began. Existing migrations and lifecycle functions are unchanged.

## Prerequisites and naming

Install the repository's reviewed authenticated identity, account/recipient identity, Engineer portal, optional purpose, canonical Office inventory, verified inventory (`202610200001`), consumables category/SKU/archive, and equipment import (`202610240001`) migrations first. Preserve their deployment preflights, including the verified existing Office UUID; do not copy a disposable fixture UUID. The migration fails if the required functions/archive table are absent or authoritative identity/inventory/stock tables have disabled RLS. Apply this additive migration once in the reviewed deployment transaction. It is intentionally not a rerunnable setup script.

New tables use `public.mcpa_wa_*`; request RPCs use `public.mcpa_wa_*`; helper functions use `mcpa_auth_private.wa_*`. The explicitly versioned import adapter uses `public.mcpa_import_equipment_v2` and `public.mcpa_import_equipment_v2_receipt`. New issue mappings and receipts reject UPDATE, DELETE and TRUNCATE. Clients have no direct write grants on new tables, and helper execution is revoked from PUBLIC/anon/authenticated/service_role.

Every RPC authenticates through the established active `profiles.auth_user_id = auth.uid()` identity. Mutation permissions are checked in SQL independently of the UI. A profile share lock and repeat identity check prevent account deactivation during an operation. The migration grants the public RPCs only to `authenticated`; those functions restrict roles further. Engineers and Architects see only their own requests through RLS and snapshot RPCs. Admin sees all Workstream A requests and audit metadata. Secretary and Tool Handler have no Workstream A entry points. Existing table policies are preserved.

## Authoritative records and transaction boundaries

`equipment` remains the physical asset inventory. `mcpa_movement_reservations.equipment_id` remains the unique reservation boundary shared with existing movement actions. New quantity requests add demand metadata only; they do not reserve stock before Admin allocation. The allocation RPC acquires the existing movement advisory lock `(672341,2026)`, then locks request/equipment rows, rechecks exact compatibility, stock and active receiver/project assignment, creates an established request movement with the selected physical equipment relations, and calls the existing public approval RPC. Established approval creates the only authoritative reservations and approval activity. An exception rolls the entire transaction back.

`consumables.current_stock` remains the only consumables balance; `consumable_stock_movements` remains the only stock ledger. `mcpa_wa_material_requests/items` describe outbound demand and approval. Existing `consumable_requests` describe incoming procurement/restock receipts and are left intact. `mcpa_wa_material_issues` stores metadata linking each issued request line to exactly one existing stock movement; it does not store another quantity/balance. Issued quantity is derived from the linked negative ledger delta. Issuance uses the existing permitted ledger `kind='usage'` for compatibility, while the new issue mapping identifies this as issuance, not confirmed consumption. Confirmed consumed quantity is always unknown (`null`); no consumption records are fabricated.

For each new non-import mutation, `mcpa_wa_operations` binds a UUID to authenticated actor, action and complete JSONB payload. An operation advisory lock serializes retries before state checks. Successful retries return the exact saved JSON response; a different action, actor, item order, quantity or timestamp with the same UUID fails. All request, balance, ledger and receipt writes share the same database transaction. A rollback leaves no successful receipt, so the same UUID can be retried. After transport uncertainty, retry the unchanged payload and UUID. A deliberately new action needs a new UUID. Clients must not retry an uncertain mutation with a new UUID.

Consumables issuance locks the request header (serializes its approved remainder), then affected existing stock rows in UUID order (serializes across requests and existing stock RPCs). It rechecks archive state, current stock and cumulative prior issues before each delta. There is no stock deduction on submit or approve. A multi-line failure rolls back every line, ledger entry, mapping, header status and receipt. Stock cannot become negative. The existing stock row locks and ledger constraints protect old restock/adjustment interactions as well.

## Equipment RPCs

| RPC | Arguments | Result |
| --- | --- | --- |
| `mcpa_wa_equipment_catalog` | none | `{profile, sites, groups}` |
| `mcpa_wa_equipment_requests` | none | Array of visible request records |
| `mcpa_wa_submit_equipment` | `p_operation_id uuid, p_type_id text, p_site_id uuid, p_quantity integer, p_purpose text` | Created request record; Engineer/Architect only |
| `mcpa_wa_suggest_equipment` | `p_request_id uuid` | `{request_id, requested_quantity, eligible_assets, suggested_asset_ids}`; Admin only |
| `mcpa_wa_allocate_equipment` | `p_operation_id uuid, p_request_id uuid, p_asset_ids uuid[]` | Approved request record; Admin only |
| `mcpa_wa_reject_equipment` | `p_operation_id uuid, p_request_id uuid, p_reason text` | Rejected request record; Admin only |

`profile` is `{id, name, role}`. `sites` is `[{id, name}]` of active, unarchived projects; operational users receive only assigned projects. Submission requires the same assignment in SQL. Allocation revalidates assignment and active requester account. Quantity is 1..100, with exact positive integer typing; purpose is optional, at most 2000 characters. Availability is checked on submission and authoritatively rechecked on allocation. Pending requests may compete for available stock because they are demand, not reservations.

Groups include `type_id, type_name, name, category, brand, model, details, condition, tracking_type, unit, physical_records, requestable, available_quantity, reserved_quantity, deployed_quantity`. `type_id` is SHA-256 of the exact JSONB array of name/category/brand/model/details/condition/tracking_type/unit. It is an opaque compatibility fingerprint, not a durable master type ID. No fuzzy name or variant normalization is used. Serial numbers are per asset and excluded from compatibility. Metadata changes produce a different fingerprint; an existing pending request then needs review/rejection and resubmission rather than silent substitution. Null/empty/whitespace differences remain separate groups deliberately.

Available quantities include positive, unheld AVAILABLE/IN_OFFICE stock whose existing `inventory_lock` is null and whose condition is not damaged, repair, underrepair, missing or lost. This matches the established verified inventory guard. Unassessed/inspection conditions are preserved as their own groups; no condition value is invented. Reserved totals use established workflow lock categories, including orphan active handovers and stale protective reservations. Deployed totals use holder/IN_USE state. Diagnostic reserved and deployed values can overlap when inconsistent legacy data has both custody and a reservation; these are independent indicators, not guaranteed partitions. No stale reservation or legacy equipment is automatically repaired or deleted.

Only `Individual` records with `quantity=1` can be allocated by this feature, one UUID per physical asset. Grouped Bulk remains visible with its grouped quantity and `requestable=false`; no existing Bulk record is converted, divided or used to pretend several physical Asset IDs exist. Legacy Individual records with quantities other than one remain visible and unchanged; their group is conservatively disabled in the UI. Bulk partial reservation requires a coordinated shared inventory/custody contract and is an unfinished integration point.

Suggestions expose all currently eligible physical assets (`[{id uuid, asset_id text, name}]`) plus the first requested count of UUIDs ordered by Asset ID. Suggestions are advisory. Admin may select any distinct compatible eligible UUIDs, but must select exactly the requested quantity. Partial equipment approval is not implemented. The allocation response has `approved_quantity=requested_quantity`; stock changes between preview and allocation fail atomically.

A request record includes `id uuid, requester_id, requester_name, site_id, site_name, type_id, type_name, requested_quantity, approved_quantity, purpose, status, rejection_reason, movement_id text, created_at, updated_at, assets:[{id uuid,asset_id text}]`. Rejection requires a nonempty reason up to 2000 characters. `status` dynamically follows the established linked movement after allocation, including released/received/canceled lifecycle states; the new metadata's approval fields remain historical. Snapshot `updated_at` is the Workstream A metadata timestamp; use existing movement history for later lifecycle event timestamps.

## Workstream B handoff

Use `equipment.id` (UUID) as the stable physical identity, `equipment.asset_id` as the individually traceable existing tag, `mcpa_movements.id` (text) as the established movement, and `mcpa_wa_equipment_requests.id` (UUID) as originating quantity demand. The existing movement JSON includes `quantityRequestId`; its `toolIds` are actual Asset IDs. `mcpa_movement_assets` stores every stable equipment UUID. Existing `releaseRequest`, tested receipt, custody, return, transfer, and authorized cancellation operate on this same movement/reservation graph. Workstream A adds no custody table, modifies no Workstream B function and does not release or transfer equipment through its new UI.

## Consumables RPCs

| RPC | Arguments | Result |
| --- | --- | --- |
| `mcpa_wa_consumables_catalog` | none | `{profile, sites, catalog}` |
| `mcpa_wa_consumables_snapshot` | none | `{profile, sites, catalog, requests}` |
| `mcpa_wa_submit_consumables` | `p_operation_id uuid, p_site_id uuid, p_purpose text, p_items jsonb` | Created request; Engineer/Architect only |
| `mcpa_wa_review_consumables` | `p_operation_id uuid, p_request_id uuid, p_decision text, p_items jsonb, p_note text` | Reviewed request; Admin only |
| `mcpa_wa_issue_consumables` | `p_operation_id uuid, p_request_id uuid, p_items jsonb, p_issued_at timestamptz` | Updated request; Admin only |
| `mcpa_wa_consumables_analytics` | `p_from timestamptz, p_to timestamptz` | `{profile, sites, catalog, requests, from, to}`; Admin only |

Catalog entries are existing active consumables rows, including `id, name, item_code, category, specification, unit, current_stock, minimum_stock, stock_status, version`. Archived items are omitted; historical request line snapshots remain available. No new catalog is seeded. Existing inventory categories and unit strings are used exactly. Browse/search/category filtering can run on this snapshot without expanding shared table policies.

Submission items are `[{consumable_id uuid, quantity number, unit text}]`: 1..100 distinct active SKUs; quantity is positive, less than 1 billion, with at most three decimal places; unit must equal the registered SKU unit. Requests may exceed current stock and remain demand pending future restocking. Site must be assigned, active and unarchived. Purpose is optional and at most 2000 characters. SKU label/code/category/specification/unit are snapshotted on the line so later catalog edits do not rewrite history.

For approval, `p_decision='approve'` and items are `[{item_id uuid, quantity number}]`, with every line exactly once, quantities from zero through requested quantity and at least one positive approval. `p_note` is optional, at most 2000 characters. For rejection, `p_decision='reject'`, `p_items=[]`, and a nonempty note is required. Only pending requests can be reviewed. Current stock is checked on issuance rather than approval.

Issue items are `[{item_id uuid, quantity number}]`, with 1..100 distinct lines, each positive, within the remaining approved amount and currently active stock. Each issue may cover some lines and part of a line. Status becomes `partial` while any positive approved remainder exists, otherwise `issued`; quantities approved at zero are already resolved. A request approved below requested quantity completes at its approved amounts, preserving the original demand separately. `p_issued_at=null` records canonical server time after payload binding, supporting an unchanged null retry. Explicit timestamps must lie between request creation and current server time. Issues record Admin profile, requester, project, quantity, ledger reference and date through their linked request/header/line data.

Requests contain `id, request_number, requester_id, requester_name, site_id, site_name, purpose, status, note, reviewed_by, reviewed_at, created_at, updated_at, items, issues`. Each item has `id, consumable_id, item_name, item_code, category, specification, unit, requested_quantity, approved_quantity, issued_quantity, confirmed_consumed_quantity:null`. Pending approved quantities are zero. `issued_quantity` is always the lifetime total from authoritative linked stock movements. Each issue has `id, operation_id, item_id, stock_movement_id, quantity, issued_at, issued_by_id, issued_by_name`. An empty issue list is `[]`.

Analytics requires a nonempty increasing half-open interval `[p_from,p_to)`. All request headers and their line lifetime quantities remain in the response; only each request's `issues` array is filtered by `issued_at`. This allows a request created before the period to explain its issue during the period. For period requested/approved cohorts, independently filter request `created_at`. For period issued quantities, sum only the filtered issue events, grouped by SKU/unit, requester and site. Do not sum line lifetime `issued_quantity` for a filtered issue period. Do not sum incompatible units. Low stock is the current active catalog balance, independent of historical filters. Legacy restocks/usage without a Workstream A issue mapping cannot be attributed to a requester/site by guessing and are not invented as feature issues.

## Import expansion RPC

`mcpa_import_equipment_v2(p_operation_id uuid,p_rows jsonb)` is Admin only and takes original spreadsheet rows with existing v1 keys. Individual quantity N expands to N physical records with quantity 1. Bulk retains the original grouped quantity and creates one grouped record. Every source row needs an explicit supported condition; this avoids the incumbent blank-condition default inventing Good. Brand/model/serial remain supplied text or empty strings. An Individual row with quantity greater than one and a nonempty serial is rejected as ambiguous; unique serials require separate original rows.

Limits are enforced on the server: 1..500 original rows, original JSONB at most 2 MiB, at most 500 resulting physical/grouped records, and expanded JSONB at most 2 MiB. Original source row must be a distinct integer 2..1,000,000. Positive Bulk quantity preserves the existing signed 32-bit integer bound 2,147,483,647. Individual expansion may use at most 500 per row and must also fit the aggregate record limit. The frontend additionally validates workbook upload size; RPC byte limits concern the parsed JSON payload, not compressed workbook bytes.

The wrapper deterministically assigns private synthetic source ordinals only while delegating expanded rows to the unchanged `mcpa_import_equipment` RPC, because v1 requires a unique source number for every inserted record. A separate mapping restores the original spreadsheet row and adds `expansion_index` to each asset in the v2 result. No frontend expands or forges Asset IDs. Existing v1 validates all metadata, generates the existing `T-` plus 16 uppercase UUID hex tags, uses canonical Office defaults, preserves Admin permissions, and stores its authoritative immutable import receipt. Manual registration remains unchanged. The v2 result preserves the base fields and includes `spreadsheet_rows`, `expanded_records`, and original-row asset mapping. V1 batch validation errors may refer to a synthetic internal ordinal; user preview uses the original-row mapping.

`mcpa_wa_import_operations` stores original payload SHA-256 and exact v2 result, referencing the existing import receipt. Both receipts and all equipment inserts commit or roll back together. The wrapper takes the same operation advisory lock as v1. Reusing the UUID through v1/v2 cannot race into a duplicate; a prior v1 operation is rejected by v2. A different original payload/order/actor with the same v2 UUID is rejected even when two inputs would expand to equivalent physical rows. `mcpa_import_equipment_v2_receipt(p_operation_id uuid)` returns the saved v2 JSON or null; Admin may read import receipts, consistent with existing Admin receipt access. The browser controller additionally confines recovery to its authenticated actor. Never expose these receipts to operational roles.

## Verification and deployment limits

The owned PGlite fixture loads actual existing setup/migration SQL into a disposable in-memory PostgreSQL runtime, then this unapplied migration. `node --test --test-concurrency=1 tests/quantity-requests-v2/database.test.cjs tests/consumables-requests-v2/database.test.cjs` checks quantity groups, adjusted distinct allocation, variant/duplicate/stale guards, old movement reservation conflicts/release, role checks/RLS, operation replay, rejection, multi-line approval/partial/full issue, zero negative stock, multi-line rollback, history/analytics date boundaries and legacy procurement receipt compatibility.

PGlite's shared fixture serializes `SET ROLE` calls and has one PostgreSQL session. Its Promise submissions check stale/conflicting outcomes and retry contracts, not native multi-session concurrency. Native PostgreSQL independent-backend results, when available, belong in the implementation report and dedicated disposable harness artifacts. Neither isolated DB tests nor a browser harness implies shared runtime wiring or a live deployed feature. The production baseline, RLS, Office preflight, native concurrent behavior, Workstream B compatibility and authenticated staging end-to-end tests must be reviewed before deployment. No production SQL was executed.

Open integration limitations: no grouped Bulk partial allocation; no confirmed consumption capture; no change to existing archive UI (an outbound request can remain pending/approved while a SKU is archived; issuance then fails safely until explicit existing restoration); no new request cancellation/reapproval path; no server pagination for prototype-scale catalogs/history; no historical inference of requester/project for old unlinked stock deltas. Existing shared navigation/importer mounting and deployment are separate, documented integration work.
