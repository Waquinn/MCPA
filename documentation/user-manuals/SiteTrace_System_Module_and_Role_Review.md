# SiteTrace Web Application — System Module and Role Review

Version **1.0** · Prepared **12 October 2026 (Asia/Manila)**

## Outcome and scope

The current repository implements construction equipment accountability using authenticated company profiles, project assignments, requests, reservations, transfers, named-recipient inspection, returns, repair/loss resolution, consumable stock, procurement records and monitoring. Its actual interface is branded **MCPA / BuildRight Corp.**, not SiteTrace. The requested SiteTrace filenames and document titles have been retained; the manuals explain the name difference.

There are **14 primary sidebar modules**, **2 bundled detail screens**, and **5 supported authenticated roles**. Engineer and Architect share the same permissions. Authentication, receiving QR services, notifications, storage and synchronization are cross-cutting functions and are not counted as extra sidebar modules.

The review inspected the actual entry pages, module loader, navigation, shared services, current module handlers, account Edge Function, SQL policy/RPC definitions and existing deployment documentation. The review also rendered the unmodified interface against an isolated in-memory PostgreSQL-compatible PGlite fixture using the repository's existing test infrastructure. Local fixture construction is separate from the application's live database.

**Verification boundary:** implemented means supported by current executable source, not independently verified in production. Browser evidence confirms authorized local rendering and read paths. Write handlers were inspected; some transactions were prepared through the isolated fixture to make saved states reviewable. The capture browser rejected business writes after preparation. No production endpoint, live Auth account, migration, scheduler, Storage object or live transaction was accessed.

The protected live **REQ-00001** was not read or changed. The statement concerns this task's actions; it is not a comparison of live database state before/after.

## Authentication and account management findings

- Supabase Auth owns passwords and sessions. `mcpa_my_profile` verifies the permanent company profile and active authorized role. Unknown/unlinked/inactive profiles are denied.
- Password recovery callbacks are implemented. New-password setup requires at least 12 characters and signs the user out after saving. Real email/redirect behavior was not tested.
- There is no public registration. Company accounts are provisioned by the administrator; the app retains verified account linking, role/status editing and gated test accounts.
- Edit access preserves the person record; existing Auth links cannot be reassigned/removed through the recovery form. Self-removal of Admin authority is refused. No account deletion or general profile editor is confirmed.
- Real development-account creation supports Engineer/Architect only, requires an explicit capability and 12–128-character password, and can access company records. It is separate from offline demonstration.
- Offline demo is explicitly chosen, available for Admin/Engineer/Architect only, and uses browser-local sample data. Users, Material Requests and Purchases are excluded; Projects is read-only; receiving QR requires authenticated company service access.
- The existing PRODUCT.md statement that acting roles are unauthenticated prototype boundaries is stale relative to the current Auth implementation. Deployment/security effectiveness still requires the deployed migrations/functions to match source.

## Operational state and custody findings

1. **Request:** creation is Pending; approval reserves whole records; release creates a pending transfer and marks the request Released. Neither approval nor dispatch changes custody. Saved requests have no general edit/resubmit control.
2. **Direct transfer:** an operational sender must hold In Use equipment; Tool Handler can dispatch eligible available unheld stock. Recipient and active destination assignment are rechecked server-side. A receiving QR assists identity selection but does not move stock.
3. **Inspection/receipt:** only the named active Engineer/Architect receiver submits. Every tool requires a condition; received non-missing items require a testing check; damage/missing require notes; damage requires a custody decision. Good/accepted-damaged items move to the receiver and destination. Missing items retain source holder/location and become Missing. Follow-up cases record damage/loss.
4. **Damage refusal:** the current eligible receiver can decline damaged handover custody; the entire handover remains reserved with unchanged equipment custody/status. Inspection/refusal evidence is retained. An original field sender can reopen/cancel; a linked released-request requester can cancel. Admin/Secretary/Tool Handler cannot perform these interruption actions.
5. **Cancellation:** withdrawal records Withdrawn; reservation/transfer cancellation records Canceled and releases appropriate allocation; cancellation of a request-linked transfer closes the linked request too. Reasons/confirmation and immutable audit evidence are required. Received transfers cannot be canceled through these controls.
6. **Return:** one-step return save. Good clears holder and records destination/Available; damaged records destination and repair while retaining holder; missing retains holder/location and opens a loss case. There is no additional Admin return acceptance, return schedule or return QR stage.
7. **Repair/recovery:** Admin starts/completes repairs and records recovery. Completion/good recovery clears holder and sets Available; damaged recovery clears holder and opens repair at the recorded destination. Under repair can be a case-derived display while raw equipment remains REPAIR.
8. **Bulk equipment:** equipment movement is by whole asset record and its full quantity. No partial quantity selection, partial physical receipt or record split is implemented. Consumable stock uses a separate decimal-quantity workflow.
9. **Consumables versus purchases:** a material Purchase Request has no approval stage. Creation leaves stock unchanged; partial/full receipt increments stock; cancellation preserves already received stock. Purchases is a separate financial/reference ledger and never increments stock itself.
10. **Audit scope:** Activity Logs is movement history. Project History, Stock History, Purchase history and Account access history are separate stores/views. Only confirmed exports are documented: printable inventory receipt, monitoring-report CSV and movement-activity CSV.
